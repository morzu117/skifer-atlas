# ADR 0037 — Rattacher un espace à un dépôt vide : route, identité du créateur, dépôt vide

Date : 2026-11-04 · Statut : **acceptée** (mise en œuvre du plan 0033)

## Contexte

Un espace créé sans adresse n'a pas de dépôt distant. La route `POST /api/workspaces/{ws}/remote` existait, sans interface, et ne vérifiait presque rien : elle ajoutait `origin` puis poussait. Trois questions se posaient pour en faire un parcours (issue #137).

- **Où vit la route, et que rend-elle ?** Elle était dans le routeur de la gouvernance, et ne rendait ni le rôle relu ni le drapeau `space_referent` que l'écran lit.
- **Que devient l'identité du créateur ?** L'espace local ne connaît pas GitHub : le créateur y est inscrit dans `governance.yaml` sous l'identité locale (`ATLAS_ACCOUNT` ou `user.name` de git). Une fois l'espace rattaché, le compte de l'utilisateur dans Atlas est celui que l'hébergeur authentifie, le login GitHub (ADR 0029). Sans autre mesure, ce compte n'est pas dans la gouvernance : le créateur devient lecteur de son propre espace, ne peut plus enregistrer la gouvernance et ne peut rien autoriser.
- **Comment sait-on qu'un dépôt est vide ?** Pousser sur un dépôt qui a déjà un historique le refuse (`non-fast-forward`) ou, pire, le réécrit avec un push forcé. L'adhésion à un dépôt qui a un historique est le plan 0005, pas celui-ci.

## Décision

Le complément du 5 novembre 2026 ci-dessous précise les règles de reprise et remplace les affirmations initiales qui limitaient le rattachement aux seuls dépôts vides.

**Route.** Elle passe dans le routeur des espaces (`api/routes/workspaces.py`) avec la même adresse. Elle rend l'espace comme les autres routes de ce routeur : `role_label` et `space_referent` compris, relus dans la gouvernance sous le compte de l'hébergeur. Huit codes d'erreur s'ajoutent (un neuvième, `attach_incomplete`, vient avec le suivi de #143) : `remote_exists` (409), `remote_not_empty` (409), `workspace_dirty` (409), `wrong_branch` (409), `remote_not_found` (422), `remote_not_writable` (422), `origin_conflict` (409) et `remote_partial` (409). Les autres codes (`invalid_remote`, `credentials_in_url`, `unsupported_host`, `host_auth_failed`, `host_unreachable`, `push_failed`) existaient.

**Identité du créateur.** Le compte du créateur est réécrit dans la gouvernance (membres, référents et validateurs de domaine) dans un commit dédié, « Identité du créateur : `<ancien>` devient `<nouveau>` », poussé avec l'historique de l'espace.
- Le commit est fabriqué par plomberie (`commit_files`, comme les propositions) : ni l'arbre de travail ni l'index ne bougent avant le succès du push.
- Le push envoie `<commit>:refs/heads/<branche>`. Quand il a réussi seulement, la branche locale avance en avance rapide sur ce commit, `origin/<branche>` devient son amont, et le registre reçoit `git_remote`, le nouveau compte et le rôle relu.
- L'avance rapide réécrit `governance.yaml` dans l'arbre de travail : si le fichier a des changements locaux (enregistrés dans l'index ou non), elle échouerait après la publication, laissant un dépôt rempli, `origin` configuré et l'espace encore local, d'où un rattachement impossible à relancer. Le contrôle porte sur `governance.yaml` toujours, qu'un compte soit à réécrire ou non : une modification locale qui retire le compte local ou ajoute le compte GitHub ferait sauter le renommage, et le push publierait la gouvernance commitée alors que le rôle serait calculé sur le fichier modifié. Le contrôle refuse aussi, sous le même code, un conflit non résolu (`git ls-files -u`) ou une opération inachevée (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`). Une fois les contrôles passés, l'arbre de travail et la branche principale coïncident, et la gouvernance lue (renommage, rôle) est celle du commit publié. Le rattachement est donc refusé avant toute écriture (`workspace_dirty`, 409), avec un message qui demande d'enregistrer ou d'annuler. Un autre fichier modifié ne gêne pas : le commit ne touche que la gouvernance.
- Le commit d'identité est basé explicitement sur `refs/heads/<branche principale>`, et l'avance rapide ne fait avancer que la branche extraite. Atlas ne change jamais de branche dans le clone (les propositions passent par un dossier temporaire), mais après un `git checkout` fait à la main, l'avance rapide ferait avancer une autre branche que la principale. Avant toute écriture, `HEAD` doit donc être `refs/heads/<branche principale>` (`git symbolic-ref -q HEAD`) ; sinon `wrong_branch` (409), « La branche <x> est extraite dans le clone de l'espace : revenir sur <main>, puis rattacher le dépôt. » (« aucune (HEAD détachée) » si `HEAD` est détachée).
- Si l'ancienne identité n'est pas membre, ou si le nouveau compte l'est déjà, la gouvernance ne change pas et aucun commit n'est ajouté.
- Le commit est visible dans l'historique et dit pourquoi, au lieu d'une réécriture silencieuse. Le rôle suit le compte, non le contraire : la gouvernance reste l'unique source des rôles.

**Dépôt vide.** Avant d'ajouter `origin`, `git ls-remote --refs -- <adresse>` ne doit rendre aucune référence, ni branche ni tag ; seule exception, une publication partielle d'Atlas, reconnue selon le complément ci-dessous. Il ne laisse rien dans le clone. Le résultat de git est classé par sa sortie : introuvable, authentification, droits, sinon `host_unreachable`. La sortie brute est gardée dans `RepoError.output` (nettoyée des jetons) et n'est jamais rendue par l'API.
- Pour GitHub, l'API le complète : `GET /user` donne le compte, `GET /repos/<propriétaire>/<dépôt>` dit si le dépôt existe, s'il est archivé et si le compte peut y pousser (`permissions.push` ou `permissions.admin`). GitHub répond 404 aussi pour un dépôt privé sans accès : le message le dit.
- Un dépôt GitHub exige un jeton du coffre de l'espace (ADR 0029) ou `ATLAS_GITHUB_TOKEN`. Sans lui, `host_auth_failed`, avant tout appel à git : l'interface propose alors la connexion par le device flow, sans quitter l'écran.
- Entre la vérification et le push, un dépôt peut recevoir un commit. Le push est alors refusé, ce qui est classé `remote_not_empty` ; `origin` est retiré et rien n'est appliqué en local.
- Tout se fait sous le verrou du clone (ADR 0035), pour qu'aucun `fetch` ne passe entre `remote add` et le retrait d'`origin`.

## Conséquences

- Côté écran, le rattachement relit la gouvernance (le commit d'identité la change) : les modifications non enregistrées de l'Administration sont gardées, avec le compte du créateur réécrit comme sur le serveur, plutôt que perdues ou soumises à une confirmation. Un domaine ou un membre en cours d'édition n'est pas dans le brouillon : le rattachement est suspendu (bouton désactivé, message) jusqu'à ce que la modification soit validée ou annulée. Pendant la requête, puis jusqu'à la fin du rechargement de l'administration, le reste du formulaire est gelé (`fieldset disabled`, piloté par le parent) : le brouillon conservé est celui d'où la requête est partie, et rien n'est écrit dans un formulaire sur le point d'être remonté. Si cette relecture échoue, le formulaire reste gelé et une bannière (« Le dépôt est rattaché, mais les paramètres n'ont pas pu être relus ») propose « Réessayer » ; à la réussite, le brouillon est repris comme d'habitude.
- **Collision de compte dans le brouillon.** Si le brouillon a ajouté un membre dont le compte est le login GitHub (absent de la gouvernance avant le rattachement), le serveur renomme le créateur, mais rejouer ce renommage sur le brouillon fusionnerait deux membres, et l'enregistrer tel quel remettrait l'ancien compte au créateur : il perdrait l'administration. Le brouillon n'est alors pas repris : la gouvernance du serveur est rechargée, avec l'avertissement « Vos modifications non enregistrées n'ont pas été reprises : le compte <login> figurait déjà dans le brouillon. Refaites-les à partir de la gouvernance du dépôt. » Aucun rôle n'est fusionné. Sans collision, le brouillon est repris.
- **Limite acceptée : la course entre `ls-remote` et `push`.** Git n'offre aucune vérification atomique « le dépôt est vide » ; on ne cherche pas à la fermer. Si un autre client crée la branche principale entre les deux, le push est refusé (pas de push forcé) : `remote_not_empty`, rien n'est appliqué en local. S'il crée une autre branche ou un tag, le push réussit : l'espace est publié et rattaché, rien n'est écrasé ni perdu, mais le dépôt contient alors une référence qu'Atlas n'a pas vue au moment de la vérification (un historique sans lien avec celui de l'espace). Le cas demande une action concurrente sur un dépôt censé être vierge ; il est consigné, non traité.
- Avant publication, un refus ne modifie pas le clone. Après publication, une étape peut échouer et laisser `origin` ou la branche avancée ; la reprise ci-dessous termine alors le rattachement, et l'API le dit par `attach_incomplete`.
- Un dépôt créé avec un README, une licence ou un `.gitignore` est refusé : le message le dit. Rattacher à un historique existant reste hors du périmètre ; il demanderait une décision sur la fusion de deux historiques.
- Le premier commit de l'espace distant n'est pas celui de la création : l'historique distant contient aussi le commit d'identité quand le créateur avait un compte local. Les tests e2e le vérifient dans le dépôt nu.
- Une règle de branche par défaut (protection avec pull request obligatoire) fait refuser le push. Le message est celui de `remote_not_writable` ou de `push_failed`, selon la sortie de git ; un message dédié viendra avec un dépôt de test réel.
- L'état du rattachement réel (push vers un dépôt GitHub vide, `permissions` réelle, SSO d'organisation) n'est vérifié qu'avec un faux GitHub et des dépôts nus locaux. Il figure au « Reste à faire ».
- Aucun import dynamique n'est ajouté : le sidecar PyInstaller est inchangé.

## Complément du 5 novembre 2026 — reprise idempotente

Un push peut avoir été accepté sans que sa confirmation arrive, et une étape ultérieure peut échouer. Tant que `git_remote` est absent du registre, une nouvelle tentative vers la même adresse peut terminer le rattachement. Les contrôles de branche, de gouvernance et d'opération en cours restent préalables à toute écriture. Un `origin` existant est réutilisé si son adresse correspond à celle demandée, à une écriture équivalente près (voir le complément « suivi de #143 ») ; une autre configuration est refusée par `origin_conflict` (409). Le registre reste la source de vérité pour `remote_exists`.

Un dépôt non vide ne peut être repris que s'il n'a qu'une seule référence, la branche principale. Si elle pointe sur la tête locale ou sur un ancêtre strict de celle-ci, Atlas pousse les commits locaux en avance rapide si nécessaire. Si la gouvernance doit encore être renommée, il crée et pousse d'abord le commit d'identité ; une publication nue ne peut donc pas supprimer le rôle du créateur. Aucun push n'est forcé.

Atlas reconnaît aussi un commit d'identité dont l'unique parent est dans l'historique local : seul `governance.yaml` change et son contenu est exactement le résultat du renommage du compte local vers un membre publié. L'inspection se fait dans un dépôt temporaire, sans modifier le clone. Si le parent est la tête locale et le compte publié est le compte courant, Atlas récupère le commit et avance la branche. Si le clone a divergé depuis son parent, `remote_partial` (409) demande de résoudre la divergence (« clone évolué » quand la branche locale a avancé depuis le parent, « clone divergé » quand le parent n'est plus ancêtre de la tête locale, voir plus bas) ; si le compte courant a changé, ce même code indique le compte publié et demande de s'y reconnecter. Ce contrôle s'applique aussi quand la branche locale a déjà avancé sur le commit d'identité. Une autre référence ou un historique étranger reste `remote_not_empty`.

La reconnaissance structurelle ne prouve pas l'auteur : une publication identique créée autrement est également reconnue. Elle peut refuser une reprise si la gouvernance ou l'historique ont évolué autrement. Après un échec de push ambigu, `ls-remote` confirme le succès seulement si l'unique référence est la branche attendue au commit poussé ; sinon l'erreur subsiste. Un refus explicite n'est pas considéré comme ambigu. Pour un commit déjà présent localement, l'inspection ne fait aucun fetch. Sinon, elle télécharge seulement la pointe et son parent par un fetch superficiel dans un dépôt temporaire, sans leurs gros fichiers (voir plus bas) ; un parent inconnu du clone est refusé. Pour une identité reconnue, le fetch normal dans le clone récupère le commit sans le rendre superficiel ; un échec de ce fetch après publication laisse l'état reprenable (`attach_incomplete`). Une course entre la vérification et les opérations distantes reste possible : Git ne fournit pas de transaction sur l'ensemble des références.

## Complément du 5 novembre 2026 — suivi de #143

**Deux `remote_partial` sans compte en cause.** Hors des cas de compte et de clone, `remote_partial` (409) signale aussi que la branche distante a bougé entre deux lectures de Atlas :
- « branche changée pendant la vérification » : le `fetch` d'inspection ramène un commit qui n'est plus celui que `ls-remote` annonçait ;
- « branche changée pendant le rattachement » : après la publication, le `fetch` de reprise ramène un commit autre que celui reconnu.

Dans les deux cas rien n'est modifié ; le message demande de réessayer.

**Clone divergé.** Un commit d'identité reconnu (parent unique connu du clone, seul `governance.yaml` changé, contenu exact) dont le parent n'est pas ancêtre de la tête locale, comme après un `git commit --amend` ou un `git reset` local à la suite d'une publication interrompue, lève `remote_partial` « Clone divergé », et non `remote_not_empty` : le dépôt est bien celui d'Atlas, c'est le clone qui ne le suit plus. Ce contrôle précède celui du compte. Le cas « clone évolué » (parent ancêtre de la tête, branche locale avancée sans lien avec le commit publié) garde son message.

**Gros instantané étranger : fetch filtré.** Le fetch d'inspection de profondeur 2 porte `--filter=blob:limit=1k`, dans le dépôt temporaire seulement : sur un gros dépôt étranger qui n'a que sa branche principale, il ne télécharge plus tous les fichiers de la pointe et de son parent, et le délai de 120 s ne masque plus `remote_not_empty` par `host_unreachable`. Décisions :
- Le dépôt temporaire a un `origin` nommé. Avec l'adresse seule, Git prend l'adresse pour nom du dépôt « promisor » et refuse un chemin local (`promisor remote name cannot begin with '/'`, observé avec Git 2.54) : le filtre accepté aurait fait échouer le fetch en test.
- Un serveur qui ne prend pas en charge le filtre l'ignore avec un avertissement et envoie tout : le fetch reste valide (HTTPS GitHub, `file://` ou chemin sans `uploadpack.allowFilter`). Si le fetch filtré échoue autrement (sortie non reconnue, hors délai dépassé), il est retenté une fois sans filtre. Après un délai dépassé, pas de nouvel essai : le délai serait doublé.
- `diff-tree` ne lit que des arbres, que le filtre ne retire pas. Le contenu de `governance.yaml` du commit d'identité se compare par **identifiant d'objet** : `ls-tree` donne celui du commit, comparé à celui que `git hash-object --no-filters` calcule sur `dump_governance(...)` pour le renommage vers le compte courant. Aucun blob n'est lu, que le fichier fasse plus ou moins de 1 Ko. Le parent est lu dans le clone, qui le connaît.
- Seul un autre compte publié que le courant exige de lire le fichier (pour le nommer dans `remote_partial`). Omis par le filtre, il est alors récupéré seul par Git depuis le dépôt « promisor » du dépôt temporaire. Si cette récupération échoue (serveur qui refuse une demande par identifiant), le commit n'est pas reconnu et le dépôt est refusé (`remote_not_empty`) : limite acceptée, ce cas cumule un compte différent et une gouvernance de plus de 1 Ko.
- Compatibilité : `fetch --filter` et `remote add` existent avant Git 2.30 (`MIN_VERSION`). Les tests ont tourné avec Git 2.54 seulement ; ils couvrent le filtre accepté (`uploadpack.allowFilter`) et ignoré.

**`origin` : écritures équivalentes, adresse montrée.** La comparaison de l'adresse d'`origin` à l'adresse demandée passe par `normalize_remote_url` (`repo/git.py`) : un `.git` final, un `/` final et la casse du schéma et de l'hôte sont sans effet (HTTPS, SSH, syntaxe scp). Le chemin garde sa casse ; un chemin local garde son `.git` (deux dossiers possibles) mais perd son `/` final ; un identifiant dans l'adresse la rend différente. Le contrôle est local et passe avant tout appel réseau, y compris l'API de l'hébergeur (jeton ou compte), `ls-remote` et `fetch`. Le message d'`origin_conflict` montre l'adresse trouvée (ou « aucune adresse », « plusieurs adresses », « adresse d'envoi distincte »), avec l'identifiant remplacé par `***` (seul `git`, l'utilisateur SSH habituel, reste), la query string par `?***` et le fragment par `#***` (un jeton peut y avoir été mis à la main). `mask_remote_url` est le seul chemin par lequel une adresse configurée atteint un message ; les messages de `remote_partial` et d'`attach_incomplete` n'en contiennent aucune, et les journaux ne portent que l'étape et le code. Il n'y a ni route ni action de remise à zéro du rattachement : le message dit comment corriger `origin`, et une remise à zéro fera l'objet d'un plan à part.

**Erreurs après publication : `attach_incomplete` (409).** Dès que le push est accepté, ou que la reprise constate une publication reconnue, tout échec de `update-ref` ou `fetch`, `merge`, `branch --set-upstream-to`, de la lecture de la gouvernance ou de l'écriture du registre lève `attach_incomplete`, plutôt que `git_failed` (500, absent de `ERROR_STATUS`), `fetch_failed` (502) ou une `OSError`. Le message dit que le dépôt est publié, nomme l'étape et annonce qu'un nouvel essai termine le rattachement sans refaire la publication. La sortie de git n'est jamais rendue (elle peut porter un jeton) et n'est pas journalisée : seuls l'étape et le code ou le type de l'erreur le sont. Le statut 409 est celui de `remote_partial` : l'état du clone (publié, espace local) demande une reprise, il ne s'agit ni d'une faute de la requête ni d'un hébergeur injoignable. `remote_partial` (« branche changée pendant le rattachement ») reste lui-même. Côté écran, `messages.ts` traduit le code ; `origin_conflict` et `remote_partial` y montrent le message du serveur.
